# WealthOS security notes

Current [0.6.2 verification](RELEASE_0_6_2.md) includes a reproduced/fixed interrupted privacy-write defect. Startup now recovers committed lock/amount-hiding flags when only Android's legacy atomic backup remains. Isolated recovery cases passed on API 29/36, and the access-gate/secure-window regression passed. No financial schema, database-key format or cryptographic parameter changed. The review is first-party and bounded; an independent audit has not been performed.

Milestone 6 retains the on-device encryption/key model and schema 6, and adds authenticated portable backups in a pure JVM security module using platform JCA. See the [portable format and restore boundaries](BACKUP_FORMAT.md), [release/recovery procedure](RELEASE.md), [public-data architecture](MILESTONE_5_ARCHITECTURE.md) and [source usage decisions](MILESTONE_5_SOURCES.md). Public networking is optional and defaults off. No new third-party cryptography dependency, key alias, backend, telemetry or private financial upload was introduced.

## Implemented

### Statement reader (0.6.9)

Original HDFC Bank/Tata Neu HDFC XLS and matching UTF-8 CSV are selected explicitly through Android's document picker. The parent bounds file input to 256 KiB and sends bytes to a non-exported, isolated-UID service. That process has no inherited INTERNET permission or access to the vault. It checks its isolation at startup, has an independent 12-second watchdog and exits after returning the result. Parent waits are bounded and provider streams close on cancellation. Incoming results are reconstructed with domain validation and checked against a parent-computed file hash. Expired picker requests never import an unsolicited URI.

Apache POI 6.0.0 is used only for the verified single-sheet binary HSSF read path. Embedded streams/macros, encryption, formulas and unsupported cell types are rejected; no formula evaluator, links, charts or image renderer is used. Reader allocations/text/row/column/result sizes are bounded, POI logging is disabled, and only generic errors cross into the UI. Numeric Excel cells are converted to canonical decimal text with an exact binary re-encoding check before strict paise validation; accounting remains decimal. Isolation contains parser failures but does not establish absence of all vulnerabilities. Official [POI guidance](https://poi.apache.org/security.html) recommends containment of untrusted-document processing.

Only normalized selected-month lines and append-only review decisions enter SQLCipher. Imports do not post bank cash, alter card debt, change investment holdings or merge themselves into the legacy cash-flow summary. Whole-file/month duplicates are rejected; same-source row overlaps require an explicit keep/exclude decision. Source nicknames are user-selected, not verified account identities. Statement descriptions/references are sensitive local records; raw files and unnecessary account/customer/card fields are not persisted or logged. Backup schema 8 includes all four new tables and typed restore validation; portable encryption parameters are unchanged.

Resolved new runtime artifacts are POI 6.0.0, commons-codec 1.23.0, commons-collections4 4.6.0, commons-math3 3.6.1, commons-io 2.22.0, SparseBitSet 1.3 and log4j-api 2.26.1 (no log4j-core). Their supplied licenses/notices or published POM declaration are retained in `app/src/main/assets/licenses/statement-reader.txt`. This is a bounded first-party integration review, not an independent security audit.

* SQLCipher encrypts the entire Room database. A cryptographically random 256-bit database password is generated locally; it is never derived from account names or hard-coded.
* A separate AES-256-GCM Android Keystore key wraps the database password with fresh provider-generated IVs and authenticated version context. The envelope is atomically stored in app-private `noBackupFilesDir`. Keystore material is non-exportable; hardware backing depends on the device.
* Existing database/key errors fail closed. Missing or invalid key material does not cause an existing database to be deleted, reset or replaced. Room migration failures also preserve the database.
* Initial key read/create/wrap/write is serialized across loader instances within the app process. A reproduced concurrent-startup regression checks eight independent loaders against the same persisted key; the lock does not change an existing key or its envelope format.
* Optional native biometric/device credential authentication gates the UI on launch and after leaving the app. It relies on an existing Android screen lock. The wrapping key itself is not authentication-bound. Financial data remains in app memory while the process is alive.
* `FLAG_SECURE` protects screenshots and recents previews. The obscure-amounts setting hides values, chart history and free-text observation notes in read views. Form entry intentionally displays the value being entered.
* Public requests use fixed generic HTTPS URLs, strict bounds/types, normal certificate validation, no redirects and no supplied credentials/cookies. No financial uploads, trackers, unnecessary bank identifiers, passwords or OTP fields. No startup/background network requests. Public cache and explicit financial applications remain distinct, with provenance and transactional audit. Imported file publishers are explicitly unauthenticated.
* `allowBackup=false` plus explicit legacy backup and Android 12+ cloud/device-transfer exclusions. Database keys live in the no-backup directory. Privacy preferences use an atomic no-backup file.
* Portable exports use a password-derived 256-bit key (PBKDF2-HMAC-SHA256, 600,000 iterations, fresh 32-byte salt) and AES-256-GCM (fresh 12-byte nonce, authenticated version/length header, 128-bit tag). No device key is exported. Inputs are bounded; whole-file authentication precedes parsing. Native user-chosen SAF output is reopened and compared before success; only ciphertext is written outside the vault.
* All 31 tables are captured in one transaction. Restore uses trusted packaged schema/DDL, bound row inserts, encrypted staging, explicit migration handling, domain/relationship validation, a current-vault fingerprint and one atomic replacement transaction. A verified encrypted safety copy of the previous vault is required first. Imported networking consent is reset off; UI-lock/privacy preferences remain local. Failure never invokes destructive migration or resets the existing key.

## Limits and remaining release requirements

This is release-hardening work, not an independent security certification. Keystore protection alone cannot recover after uninstall, clearing storage, key loss or device loss. Recovery requires a separately retained, validated portable backup and its original password. Forgotten backup passwords cannot be recovered. In-app restore currently requires an open receiving vault; preserve an unopenable old vault and use a fresh installation/device for a known-good portable file. No destructive reset is offered as a shortcut.

An unlocked/rooted/compromised OS or instrumented process can access displayed/plaintext data and potentially use keys. SQLCipher retains key bytes in the open helper during the database lifetime. App lock is an interface gate, not a new SQLCipher password, and does not promise protection from a process compromise. Do not claim that emulator tests establish hardware Keystore assurance.

Before production: review the actual [Milestone 6 verification](PROGRESS_MILESTONE_6.md), independently protect copies of the user's now-created signing identity and passphrase, exercise physical devices (including biometric cancellation/background behavior and 16 KiB pages), review TalkBack/localization and obtain independent security review. [The signed local artifact](PRODUCTION_RELEASE.md) passed package/signature verification without reading its private key. Backup passwords use transient, non-saveable Compose state, clear on background and are best-effort wiped as arrays; immutable strings, other form state, provider internals and the heap do not provide secure memory-erasure guarantees. Safety copies are retained without automatic pruning and need explicit export to survive uninstall. A killed process may leave an encrypted staging orphan, never a plaintext backup.

Release signing is a separate local operation: see [coexisting identity and signing controls](RELEASE_SIGNING.md). The optional release ID isolates its Android sandbox and Keystore namespace from the installed development app. The scripts reject development certificates, pin the expected public certificate, review the actual packaged manifest/backup exclusions and refuse overwrites. They do not read a phone, export an app database or create a production key automatically. Signing provider memory and a compromised host remain outside their guarantees.

Subsequent [16 KiB runtime checks](16K_VERIFICATION.md) passed 58 storage/seven network cases on API 35, the same 18 isolated UI cases on both API 35/36, and native minified backup restoration on both versions, with a byte-identical product APK. The full API 35 UI pass used the separately verified stable emulator 37.2.12 and current test harness. These Google x86_64 images simulate 16 KiB userspace; they do not establish physical ARM or hardware-Keystore behavior. Earlier API 35 instrumented ART/JIT crash causation remains unconfirmed, and that image still exhibited Google/system-process crashes and a System UI ANR. Passing tests do not certify overall runtime stability or replace physical-device review.

Dependency versions are pinned; the Gradle distribution has its official SHA-256 pinned in the wrapper. Current source documentation is evidence for selection, not a substitute for successful resolution, compilation and device tests. This milestone does not imply a full dependency security audit.

Gradle 9.6 is deliberately pinned to AGP 9.4's documented default and within Kotlin 2.4.21's supported Gradle range. Lint's notice about newer Gradle 9.8.2 is informational; that newer version is beyond the Kotlin documentation's fully supported 9.7 maximum. Android modules use AGP's built-in Kotlin, with no external Kotlin Android plugin. The pure JVM module and Compose compiler use Kotlin 2.4.21. Lifecycle is pinned to stable 2.11.0. The UI test runtime explicitly selects Espresso 3.7.0, overriding Compose's older transitive 3.5.0, which fails input initialization on the installed Android 16 image.
